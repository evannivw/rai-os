# Blocking receive, wakeup and bounded deadlock handling

Implemented October 28, 2026. A task can now wait for a message without repeatedly
running a receive loop. Its saved context and private stack remain in RAM. The
scheduler excludes Waiting records until the kernel completes their pending call.

This implements the next dependency in [ROADMAP.md](ROADMAP.md): protected tasks
can communicate, so a future service can now wait for work. It remains a closed,
bounded two-task batch rather than a persistent service receiving external events.

## Try it

```sh
sh scripts/console.sh
```

Then enter:

```text
ipc.wait
ipc.check
schedule.isolate
```

The new command starts A first. A makes one blocking receive call and stops being
selected. B sends kind=1/value=41. The kernel transfers that queued message into
A's saved result registers and marks A Ready. On its next turn A resumes after
the same SVC, validates sender/kind/value and sends kind=2/value=42 to B. Both
exit with code=0; a_value=41 and b_value=42 report actual received values.

In the captured normal runs the trace was:

```text
AD,BS,AW,AS,BR,AE,BE
```

| Entry | Meaning |
| --- | --- |
| AD | A ran, issued receive_wait and became Waiting. |
| BS | B ran and sent its message. |
| AW | Kernel completed A's pending receive; A became Ready. No user instruction ran here. |
| AS | A resumed after its receive and sent the reply. |
| BR | B received the already-queued reply immediately. |
| AE,BE | A and B exited normally. |

The report adds blocked=1, woken=1, closed_wakes=0 and deadlocked=0 for those runs.
The normal command makes two IPC calls per task; it never needs Empty polling.
The older ipc.check behavior stays unchanged. Timing-dependent timer returns may
appear in traces; this is not a CPU-time, battery or performance comparison.

## Syscall and state contract

Only ipc.wait's task runtime accepts SVC #0 with x8=12 (receive_wait). It takes no
inputs; input x0-x3 are ignored. On completion its result layout matches receive:
x0 status, x1 sender, x2 kind, x3 value on success; errors return status with x1-x3
zero. Existing send=10, nonblocking receive=11 and exit=2 remain available here.
Other modes retain their previous ABI; an unrecognized syscall faults its task.

1. If a message is queued, consume the oldest and return immediately.
2. If the inbox is empty but an authorized sender remains live, record Waiting.
   Count this syscall once, retain its saved return PC, and do not dispatch it.
3. After a sender successfully enqueues a message, complete the pending receive
   from the queue, set its result registers and transition Waiting to Ready.
4. If no authorized live sender remains and no queued message exists, complete
   with Closed (status 5). This can happen immediately or wake a pending receiver.

An already-queued message is delivered even if its sender subsequently closed.
A failed send never creates a wakeup. Exited, faulted or limit-reached tasks close
their endpoints; waiting tasks do not. A wake does not reset the timer count or
add another syscall. A second wake without a new wait is an invalid transition.
The sixteenth IPC attempt still terminates before servicing it, and the sixth
timer preemption still terminates a running task. Closure of that task also wakes
any pending peer that can no longer receive a future message.

The kernel owns queues and task records. Empty checking, entering Waiting,
enqueuing and completing wakeups execute with interrupts masked on one CPU.
There is no intervening EL0 execution in that sequence. This avoids a gap where
a message could arrive between checking an empty queue and registering the wait.
A multiprocessor design would require new synchronization and ownership rules.

## When both tasks wait

This diagnostic has no external sender, UART-to-inbox injection, device wake
source or pending timed event. If neither task is Ready and receivers remain
Waiting, no future message can be generated by the batch. The kernel marks those
records Deadlocked, closes their endpoints, records X events and returns to the
console. The mutual-wait fixture reports AD,BD,AX,BX and two deadlocked tasks.

This is an explicit termination policy for the closed diagnostic. A future
service waiting for a real external event must not be cancelled merely because
all user tasks are asleep. That design needs an event source, cancellation/time
rules, an idle path and persistent task lifetime. No WFI idle loop, hardware
sleep state, wall-clock receive timeout or energy saving is claimed here.

## Code boundaries and memory safety

- ipc.rs: pure queue-first receive_wait result, distinguishing pending from Closed
  using configured routes and live endpoints. It does not own scheduler state.
- schedule/lifecycle.rs: Waiting/Deadlocked and checked wake/deadlock transitions;
  only Ready tasks can start. Budget counts survive waiting and wakeup.
- schedule/runtime.rs: completes pending results after send/closure, records wake
  events, and applies closed-batch deadlock policy. Frame validation and MMU root
  selection still happen before each resumed EL0 turn.
- schedule/wait_programs.rs: linked Rust clients and failure fixtures. It reuses
  the inline syscall helpers and passes only scalars; no new unsafe memory-copy
  boundary or user pointer access was added.

Waking writes x0-x3 in the protected saved frame. It preserves return PC, stack
pointer, status and other registers. The private writable task maps remain active
on every user turn. Task IDs, route masks, FIFO capacity and endpoint ownership
are unchanged. Trace storage encodes task ID plus event in one byte and reserves
92 entries; that covers the bounded dispatch returns, wakeups and cancellations
without expanding the previous 92-byte trace-array storage. Physical ownership
remains twelve immutable table pages and 244 free pool pages.

## Verification

```sh
python3 scripts/verify_wait.py
python3 scripts/verify_wait.py --release
```

Each profile passed four pure mailbox tests and five lifecycle tests, including
pending versus immediate delivery, queued messages after sender closure, invalid
sends, routes without live senders, waiter exclusion, exactly-once wake transitions,
preserved budgets and terminal deadlock state.

Eight actual QEMU images per profile cover normal wakeup, mutual waiting, peer
exit, peer fault, peer infinite loop, peer syscall limit, a prequeued message and
an invalid send before the valid send. Each image runs three batches; the normal
image also runs a direct shell batch, totaling 25 per profile. The host replays
traces independently: waiting tasks cannot run; W follows the peer's send; C
requires a terminal peer; X requires the absence of ready work. It checks results,
counters, call/timer limits and exact architectural peer-fault reports.

In the infinite-loop case B receives six timer preemptions while A remains waiting
with zero timer turns and one receive call. B's limit then wakes A with Closed.
The syscall-limit case similarly closes B after its sixteenth attempt. Invalid
send does not wake A; the valid send subsequently does. Repeated normal/failed
batches confirm fresh task/queue state. Subsequent nonblocking IPC, user program,
register scheduling, private-stack checks, memory diagnostics and echo remain
usable with unchanged MMU snapshots. Extra arguments are rejected.
